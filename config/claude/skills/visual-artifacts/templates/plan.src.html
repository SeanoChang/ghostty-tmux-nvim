API Rate Limits Plan
Plan · API platform

Rate limits for the public API

Each API key gets a per-route budget of requests. The gateway asks a shared limiter before it forwards a request. Over budget, the client gets a 429 with a time to retry.

Why · 2 requests

one customer script sent 40k requests a minute to /v1/orders last Tuesday and took orders down for everyone

the on-call engineer · incident review

we need limits per API key, not per IP. half our partner traffic comes from one NAT address

the API owners · Slack

    Design

    Decisions

    Two choices are settled. Two more are open, on the claims they change: D3 on claim 1 and D4 on claim 2.

    D1

    Where the counters live

    Decided

    Choice: token buckets in Redis, one Lua script per request. Why: the gateway runs 6 replicas. A counter inside one process sees about a sixth of a key's traffic, so each key would get six budgets.

    Options considered (3)
    OptionGivesCosts
    Redis token bucket · chosenOne budget per key across all replicasOne Redis round trip per request, about 0.4 ms in the same zone
    In-process countersNo network callSix budgets per key; the limit drifts each time replicas scale
    Vendor gateway pluginNo code to ownLocks the gateway version; no per-route config
    D2

    How the limiter counts

    Decided

    Choice: a token bucket. Why: it allows a short burst up to the bucket size, then holds the average rate. A fixed window lets a key send two budgets across a window edge.

    Options considered (3)
    OptionGivesCosts
    Token bucket · chosenBursts up to the bucket size; a smooth averageTwo numbers per key: tokens and last refill time
    Fixed windowOne counter per key per windowDouble budget at each window edge
    Sliding logExact countsOne entry per request; memory grows with traffic

    Build

    Verify and roll back

    Run the tests, then a load test against staging. A flag turns the limiter off in seconds.

    go test ./... -race
    echo "GET https://staging.api/v1/orders" | vegeta attack -rate=120/s -duration=30s -header "Authorization: Bearer $KEY" | vegeta report
    flagctl set gateway.ratelimit.enabled false   # rollback: requests skip the limiter

    The load test sends 3,600 requests in 30 seconds. Expect 1,600 to pass: the burst of 100, plus 50 a second for 30 seconds. The other 2,000 get 429.
